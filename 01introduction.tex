\section{Introduction}
\label{sec:introduction}

\subsection{Motivation and Problem Statement}
% Companies try to use LLMs (AI Agents) to accelerate their software development process, but there is a lack of concepts and best practices for how to do this effectively
% Developers who are not familiar with a new software project, have to invest a lot of time and effort to learn the project structure, code base, etc. before they can contribute effectively
% LLMs could potentially help with this, but it is not clear how to use them effectively in this context, especially in large software projects like CrypTool-Online

Within a few years, coding assistants based on \acfp{LLM} have evolved from line-by-line autocompletion into increasingly autonomous software-engineering agents. Tools such as Claude Code, Codex, or OpenCode can inspect existing repositories, plan and implement changes across multiple files, execute build and test procedures, and react to the results within a single task given in natural language. Both companies and open-source projects are adopting these agents in the hope of accelerating software development. However, empirical evidence regarding their effectiveness in practice is still limited. Most research so far is benchmark-driven: Benchmarks such as SWE-bench~\cite{Jimenez2023SWEbenchCL} measure whether an agent can resolve individual GitHub issues, but they provide little insight about sustained contribution to a real project with its own conventions, tooling, and development history. Moreover, there is little guidance on how such agents should be configured and integrated into an existing project. Initial exploratory studies on the configuration of agentic coding tools~\cite{Galster2026ConfiguringAA, Lulla2026OnTI, Lulla2026TheIO} indicate that practitioners are developing best practices in an ad hoc manner, without an established body of knowledge to draw on.

A second, older problem exists independently of so called \ac{AI} tooling. \todo{Introduce AI tooling before using the term.} A developer who joins a large software project spends a considerable part of their initial effort not on writing code but on learning: the structure of the repository, the conventions of the code base, the build and test tooling, and the existing abstractions that a new feature is expected to reuse. This ramp-up cost grows with the age and size of the project, because mature projects accumulate conventions that are rarely written down completely. \ac{CTO} is such a project. It is a large, long-lived web application that offers a collection of cryptographic apps for educational purposes. The code base comprises approximately 79,000 lines of code\footnote{Physical lines excluding blank lines and comments, counted with \texttt{cloc} 2.10 on commit \texttt{9d297a17} (2026-10-20) of the cryptool.org repository; tests (approximately. 8,700 lines) included; third-party UI snippets and data files excluded. The 312 MDX content pages, which hold approximately 10,600 non-blank lines, are not included in this figure.}. The CrypTool project itself started in 1998 with its offspring \ac{CTO} being in development for over ten years. The \ac{CTO} project has an established but only partially documented pattern for how new apps are structured and added. Open-source projects like \ac{CTO} depend particularly on lowering this barrier, since their contributors are often volunteers and students who can only invest limited time before their first contribution has to succeed.

\ac{LLM}-based agents appear to be a natural fit for this onboarding problem. They can explore a repository within minutes, infer conventions from existing code, and produce a first implementation that follows those conventions. Yet it is unknown how well they actually perform this in a project of the size of \ac{CTO}, which kind of setup makes a difference (a plain prompt, project-specific instruction files, additional skills or tools), and where they still fail or require human intervention. This thesis investigates these questions by letting several agents implement new \ac{CTO} apps under different configurations and by comparing the resulting processes and outcomes in a qualitative multi-case study. The research questions guiding this investigation are stated in the following subsection.

\subsection{Research Questions}
\label{sec:research-questions}
% 1. How can LLMs (AI Agents) be used to make it easier for new developers to contribute to a large software project, such as CrypTool-Online? Or: Can LLM agents make it easier for a new contributor to work in a large project?
% 2. What is possible with current online LLMs (AI Agents) and what are their limitations in this context?
% 3. What is possible with current offline LLMs (AI Agents) and what are their limitations in this context?
% 4. What is the effect for a reviewer after such a process is applied?

The overarching goal of this thesis is to understand whether, and under which conditions, \ac{LLM}-based agents make it easier for a new contributor to work productively in a large existing software project. This goal is broken down into the following research questions:

\begin{enumerate}
	\item[\textbf{RQ1}] Can \ac{LLM}-based agents make it easier for a new contributor to work in a large software project such as \acl{CTO}?
	\item[\textbf{RQ2}] What is possible with current cloud-based \ac{LLM} agents in this context, and what are their limitations?
	\item[\textbf{RQ3}] What is possible with current offline \ac{LLM} agents in this context, and what are their limitations?
	\item[\textbf{RQ4}] What is the effect on a reviewer once such an agent-supported process is applied?
\end{enumerate}

RQ1 is the core question of this thesis and is answered through the case studies. RQ2 and RQ3 refine it with regard to the available technology: They motivate the selection of agents and define what has to be observed during the experiments, namely where an agent succeeds autonomously, where it gets stuck, and where it needs intervention. RQ4 addresses a consequence that is easily overlooked: When an agent writes the code, the human effort shifts from writing to reviewing. Whether this shift is a net benefit for the project can only be judged if the reviewer's perspective is evaluated as well.

\subsection{Research Approach} % Maybe better than methodology, because it is not a scientific method, but a description of the research approach
\label{sec:research-approach}

The research questions are addressed with an exploratory, qualitative multi-case study. This design is chosen for three reasons. First, the use of \ac{LLM}-based agents in large software projects is a young field without established metrics for what it means to \enquote{contribute more easily}. The study is therefore exploratory, which means that rather than testing predefined hypotheses, it aims to identify which effects occur and which criteria matter~\cite{Runeson2009GuidelinesFC}. Second, the behavior of an agent depends strongly on the individual project, the concrete task, and the interaction with the developer. This is difficult to capture in aggregated numbers but well suited to detailed qualitative case descriptions. Third, a controlled experiment with enough runs for statistically meaningful results is beyond the scope of a single thesis, since each run involves a real \ac{CTO} app and a manual review of the result. Instead, a small number of cases is studied in depth and compared with each other.

Besides the case studies, the thesis has a constructive part. Based on an analysis of the \ac{CTO} code base and its conventions, a project-specific agent setup is developed (\cref{sec:development}). It consists of an instruction file (\texttt{AGENTS.md}) and the agent skills provided by Chakra~UI, the component library used by \ac{CTO}. The setup is finalized before the case studies and is not changed between runs, so that the cases remain comparable. The thesis therefore produces two kinds of results: the empirical findings of the case studies, which answer the research questions, and the agent setup itself, together with guidelines on how such a setup can be built for other large software projects.

The unit of analysis is a single case, defined as one agent implementing one \ac{CTO} app under one configuration. Two configurations are compared: a baseline, in which the agent works on the unmodified repository without any project-specific configuration, and the configured setup, in which the agent additionally has access to the agent setup described above. The second app is implemented only with Claude Code, again in both configurations. The experimental setup is described in \cref{sec:implementation}.

Each case produces several kinds of data. The analysis proceeds in two steps. In the first step, each case is evaluated against a common set of criteria, such as the autonomy of the agent, the adherence to the conventions of the \ac{CTO} code base, the reuse of existing code, and the correctness and maintainability of the result. These criteria are defined in \cref{sec:evaluation}. In the second step, the cases are compared with each other in three directions: across the three agents within the same configuration, across the two configurations of the same agent, and, for Claude Code, across the two apps. \subsection{Limitations for this Master's Thesis}
\label{sec:limitations}
% Not all LLMs can be investigated, but a selection of them (e.g., Claude Code, Codex, OpenCode, Antigravity)
% Not all approaches can be investigated, but a selection of them (e.g., with/without tools, with/without skills, etc.)
% Not all apps can be implemented, but a selection of them (e.g., 2-3 apps)
% TIP: Add: possible training-data contamination if the task's app (or a similar implementation) is publicly available.

The scope of this thesis is deliberately limited in several respects. Not all available agents can be covered. Instead, three agents are selected: Claude Code and Codex as representatives of cloud-based agents, and OpenCode as an open-source agent that can be run with a locally hosted model. Likewise, only two configurations are compared, the unconfigured agent and the agent with the developed setup, although further configurations, for example with additional tools, are conceivable. In addition, only two \ac{CTO} apps are implemented, and the second one only with Claude Code. The comparison between agents therefore rests on a single app, and the results may differ for apps of other complexity. Each case is run only once. Since agents behave non-deterministically, a repeated run with the same agent and configuration may lead to a different result. Because OpenCode is the only agent that uses a local model, differences between OpenCode and the other agents cannot be attributed to either the agent or the model alone. Furthermore, the author both develops the agent setup and evaluates the cases, which may bias the assessment. \todo{Mention mitigation, e.g. blind review or review by a CTO maintainer, if done.} The results are therefore illustrative rather than statistically generalizable. Moreover, both the agents and the underlying models evolve rapidly. Consequently, the observations reflect the versions available at the time of writing and may not hold for future releases.

\subsection{Structure}
\label{sec:structure}

The remainder of this thesis is organized as follows. \Cref{sec:background} reviews related work on \ac{LLM}-based agents in software engineering and on the configuration of agentic coding tools. \Cref{sec:foundations} introduces the necessary foundations: \aclp{LLM}, agentic \ac{AI}, skills and tooling, and the requirements of the \ac{CTO} development project. \Cref{sec:development} describes the development of the customized agent setup that is used in the case studies. \Cref{sec:implementation} presents the experimental setup and the case studies for each agent. \Cref{sec:evaluation} evaluates and compares the results across agents and approaches. \Cref{sec:conclusion} concludes the thesis and outlines future work.
